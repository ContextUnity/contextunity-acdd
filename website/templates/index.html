Regular Harnesses vs. ACDD

A regular agent harness (Claude Code, Codex CLI, Antigravity, Cursor) runs one LLM's prompt-and-tool loop, leaving discipline to prompt luck. ACDD sits one layer higher as a meta-harness — guiding every step, supplying context on demand, and verifying proof before work lands.

Unguided Agent Harnesses

Where autonomous sessions break down

  • Instructions fade mid-session — long instruction files and constraints get buried or silently ignored as context fills up.
  • Premature "done" claims — agents stop after happy-path edits without proving callers, edge cases, or tests actually pass.
  • Fragile, low-awareness edits — blind grep loops miss downstream dependencies, breaking distant modules and contracts.
  • Silent architectural erosion — duplicated helpers, boundary violations, and stale docs accumulate unchecked.
ACDD Meta-Harness

Controlled, evidence-backed engineering

  • Step-by-step gate control — every stage is an explicit node in a verified DAG; agents cannot skip ahead or self-approve.
  • Just-in-time context & rules — acdd_claim injects only the exact contract, guidance, and INV-* rules relevant to the current gate.
  • Proof required before advancing — transitions fail closed until real CLI checks (acdd_verify), JSON Schema proofs, and independent reviews pass.
  • Continuous architecture verification — acdd lint and the live SQLite code graph guard crate boundaries, callers, and doc links on every change.

Manual & Headless CLI

Step-by-step control from your terminal

Start a milestone spec or an ad-hoc fix, inspect ready cursors, claim a gate, verify tests and lint, and submit — or let acdd run spawn configured role runners across parallel waves.

terminal · bash 
# 1a. Everyday task: start directly from a goal (creates task `goal`)
acdd start --goal "Fix auth parser" --workflow hotfix --scope src/auth/

# 1b. Or multi-task spec (`milestones` is configured under `specs:` in acdd.yaml)
acdd draft milestones auth-tokens        # -> docs/milestones/AC-001-auth-tokens.md
acdd start docs/milestones/AC-001-auth-tokens.md --worktree

# 2. Check ready cursors & claim a task gate (target worktrees uniformly via -C)
acdd -C .worktrees/AC-001-auth-tokens next
acdd -C .worktrees/AC-001-auth-tokens claim goal.build --worker dev-1

# 3. Verify scoped checks (or run commands inside the worktree via `acdd exec`) & submit
acdd exec -- cargo test --test parser_tests
acdd -C .worktrees/AC-001-auth-tokens verify goal.build --test parser_tests
acdd -C .worktrees/AC-001-auth-tokens submit goal.build --action pass

# 4. Independent review & commit, or headless multi-wave runner
acdd -C .worktrees/AC-001-auth-tokens claim goal.review --worker rev-1
acdd -C .worktrees/AC-001-auth-tokens submit goal.review --action pass --evidence review.json
# acdd run --jobs 4   # spawns configured role runners across waves
Orchestrator ↔ Agents via MCP

Thin coordinator prompts, self-claiming workers

In subagent mode, the orchestrator never pastes giant specs or claims gates on a worker's behalf. ACDD's state machine coordinates every agent over MCP:

  1. Inspect ready waves (acdd_state): The orchestrator calls acdd_state(action="start" | "next") to resolve schedulable gate cursors and isolated worktree paths.
  2. Spawn workers with a thin prompt: It launches subagents (Claude, Codex, Antigravity, Cursor) passing only (run, node_cursor, worker_id, worktree).
  3. Worker self-claims context (acdd_claim): Each agent calls acdd_claim first and receives its budgeted Markdown ClaimResp (contract, architect slice, findings, blackboard, and graph lenses).
  4. Verify, coordinate & submit: The worker edits inside its worktree, runs acdd_verify, logs decisions or rebuttals on acdd_blackboard, and advances via acdd_submit — handing off to an independent reviewer.
What is a Spec? · Configured in acdd.yaml

Git-tracked Markdown contracts for multi-task waves

A Spec splits a large feature into AC-* criteria and parallel ### task: blocks with disjoint write scopes (parsed by crates/acdd-spec across 4 library crates + 1 binary). acdd init sets up specs.milestones (docs/milestones/AC-001-...md) and specs.plans — scaffold via acdd draft <spec> <slug>, plan with the spec_planning template, or run preset: spec for stateless validate/roadmap/draft without creating .acdd/state.sqlite.

02 · ACDD Index

Polyglot Tree-sitter graph built for speed and freshness

Every admitted file is parsed into a single incremental SQLite graph (.acdd/code-map.sqlite) linking AST symbols, calls, documentation sections, and cross-repo libraries.

01 · Extraction Pipeline

How languages are indexed

Native Tree-sitter grammars extract declarations, imports, calls, and receiver bindings, while typed framework manifests resolve framework conventions (Django, HTMX, Alpine, Vue/Nuxt, GridViewSpec). Mixed templates ({% raw %}{% ... %}{% endraw %}, {% raw %}{{ ... }}{% endraw %}) are byte-masked by TemplateMasker before HTML/JS parsing so line offsets stay exact.

02 · Benchmark Speed

Fast cold builds & 12–25ms queries

Measured on a 4,150-file polyglot corpus (72,293 nodes, 221,662 edges, 2,967 doc sections): cold build finishes in ~10.0 s median, single-file incremental delta in ~2.8 s, and warm MCP queries (code_map_search, inspect, impact, search_docs) respond in 12–25 ms p50.

03 · Auto-Refresh & Digest Safety

Always fresh without manual rebuilds

Over MCP (acdd serve), each request verifies workspace identity and adapter digest, automatically running incremental delta or full rebuilds on edits (reusing a valid inventory check for up to 5 seconds). acdd_read rejects stale snippets by SHA-256 digest, and CLI commands trigger automatic rebuilds when an index is missing.

04 · Code ↔ Docs Binding

Verified documentation edges

Markdown files are split at headings into BM25-searchable sections. Code claims and INV-* invariants resolve uniquely against indexed AST symbols to create verified governs edges surfaced directly inside code_map_inspect and code_map_explain.

05 · Multi-Repo Graphs

Linked Workspaces

Index shared libraries or companion repositories alongside your primary project via acdd.yaml. Each linked entry declares its own source roots, docs, and exclusions, resolving cross-repo imports and docs while tracking coverage separately per workspace.

acdd.yaml · linked_workspaces 
linked_workspaces:
  - name: shared-library
    path: ../shared-library

03 · ACDD Lint

How acdd lint enforces rules across code and docs

Rules declared in acdd.yaml and executable acdd-rule blocks inside Markdown docs compile into one check pass against code-map.sqlite — blocking architectural drift in gates and CI.

Full acdd lint --categories all

What gets checked

  • arch — Architectural Boundaries (8 primitives): evaluates forbid_dependency, allow_only_dependencies, single_owner, forbid_cycles, boundary_entry, must_implement, ast_pattern, and doc_integrity rules from acdd.yaml and Markdown acdd-rule blocks.
  • docs — Documentation Integrity & Governance: checks frontmatter, Markdown links and heading anchors, symbol claims against indexed code files, stale declaration line ranges, duplicate non-contract INV-* declarations, orphan invariants lacking a governs link or acdd-rule, and invalid rule YAML.
  • syntax — Tree-sitter Parse Diagnostics: surfaces syntax and grammar parse errors across all admitted source files (syntax.parse).
  • duplicates — Structural Code Clones: detects exact and parameterized duplicate code blocks across functions and methods.
  • dead_tails — Call & Test Graph Hygiene: catches unreachable symbols (dead_tails.unreachable), functions covered only by orphaned tests (dead_tails.phantom_tested), and unresolved calls (dead_tails.dangling_call).
  • cycles — Dependency Cycles: identifies strongly connected call and import components across the workspace graph (cycles.scc).

Default gate checks run arch, syntax, and docs; pass --categories all for the full 6-category workspace sweep.

04 · ACDD Workflows

Built-in workflows, gates & what agents receive in context

Three embedded workflows built into the binary (base, code, documentation) — plus ready-to-copy reference templates (audit, spec_planning, hotfix) and repository overlays under .acdd/workflows/.

base embedded · worktree · save: commit

Foundation workflow supplying default tool admission, protective limits, core execution/review guidance, and paths / claims / administration contours.

code embedded · worktree · save: commit

Full engineering lifecycle: blueprint_synthesis → parallel tasks.{build, review, deliver, rearchitect} → run_tests / polish → integration_review → handoff.

documentation embedded · worktree · save: commit

Living documentation & invariant workflow verifying symbol links, Markdown anchors (docs.links), and executable acdd-rule blocks (code.lint [arch, docs]).

audit (template) in_place · save: none

Reference read-only 3-phase security & correctness audit (recon → analyze → triage) in skills/acdd/references/acdd-workflow-examples/ with JSON Schema findings and .acdd/reports/ output.

spec_planning (template) in_place · save: none

Reference architectural planning template (synthesize → review) validating specs.* prefixes, acyclic waves, and disjoint parallel write scopes before coding begins.

hotfix (template) inherits .acdd/workflows/default.yaml

Reference overlay for localized fixes under .acdd/workflows/hotfix.yaml: keeps scoped checks and run_tests while pruning blueprint_synthesis and integration_review.
